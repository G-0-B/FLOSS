## Purpose and Method

This report treats nearly every document across the `G-0-B/FLOSS` repository and the user's Space files as unvalidated context, and distills the current, evidence-backed "best current state" from what the project's own canonical-precedence system already designates as authoritative. The repository itself contains a substantial documentation-governance apparatus — a precedence hierarchy, a truth-label system, an ADR index, and at least one prior formal doc-culling pass — so this audit builds on that existing machinery rather than re-deriving it from scratch.[^1][^2]

## The Documentation Explosion, Quantified

The repository's own agent-memory log records a self-diagnosed "doc-explosion pattern": `docs/architecture/` alone holds 31+ files, `docs/research/` holds 51+ files, `docs/adr/` holds 10+, and there were 30+ uncategorized root-level intake `.md` files at the time of the last audit, plus a ~3GB separate AI-conversation corpus. The user explicitly acknowledged this in-repo on 2026-05-10: "yea might need a bit more aggressive culling of this even more insane overgrowth than i realized. I saw it and knew it was there but just ignored it and kept repeating it," and approved aggressive culling. This is corroborated by the Space's own file inventory (43+ files, many independently re-synthesizing the same Holochain/AD4M/hREA architecture across late-2025 through mid-2026), which is a second, parallel instance of the same failure mode described in-repo.[^3]

A dedicated triage document, `docs/research/2026-05-10-doc-cull-triage-v1.md`, was produced specifically to categorize existing docs as Keep / Update / Archive / Dispose, with an explicit rule that no file moves happen until user review. This means a formal consolidation pass was already started in-repo — it is a continuation point, not a fresh start.[^4]

## The Canonical Precedence Chain (Already Defined)

The repository already answers "what is the true current best out of everything" structurally, via `docs/governance/spine-v0.5.md`, which defines an explicit conflict-resolution order:[^2]

| Precedence | Source type | Role |
|---|---|---|
| 1 | Kernel (mandatory rules) | Always-on coordination rules, non-negotiable |
| 2 | Project Spine | Invariants + enforcement expectations |
| 3 | Canonical architecture spec (SDD Master Spec) | Requirements, module boundaries |
| 4 | UpgradableArtifact schema + lints | Shared format for evolvable artifacts |
| 5 | Governance protocols | Steward recognition, consent windows |
| 6 | ADRs / RFCs | Decisions + rationale + supersession chain |
| 7 | Contracts / Schemas | Machine-checkable constraints |
| 8 | Tests + signed test results | What makes a claim "Verified" |
| 9 | Code | Implementation detail; must conform |
| 10 | Synthesis / analysis docs | Context only, unless triaged and evidence-linked |

The explicit rule attached to this hierarchy is decisive for this audit's purpose: "Anything stated outside the chain must be triaged (✅/⚠️/🔮/❌) before being cited as capability". This means every synthesis document in the user's Space — Grand Synthesis, ROI Matrix, Holistic Vision, PRIME-DIRECTIVE dump, ARF Operating Instructions v0.4.1 — sits at precedence tier 10, "context only." None of them should be treated as capability claims without evidence-linking to tiers 1-9. This single rule resolves a large share of the confusion the corpus has been generating: the philosophy and synthesis documents were never meant to be load-bearing; only the Kernel, Spine, SDD spec, ADRs, and tests are.[^2]

## Onboarding Path (Already Specified)

`docs/governance/LOADING_ORDER.md` specifies a fixed six-step onboarding sequence for any new agent, human or AI:[^1]

1. **Kernel v1.3.1** (`FLOSSI0ULLK_Master_Metaprompt_v1_3_1_Kernel.md`) — mandatory rules, identity, prime directive, evidence gate.[^5]
2. **Context Compression Packet v1.1** — design rationale, isomorphism map (Love=Interoperability, Light=Observability, Knowledge=Verifiable State).
3. **Project Spine v0.5** — invariants, truth labels, upgrade mechanics.[^2]
4. **Canonical Build Spine v0.2** — current execution synthesis, contradiction log, phase gates.[^6]
5. **Relevant ADRs**, starting with ADR-0 then ADR-1, via `docs/adr/INDEX.md`.[^7]
6. **Seed Packet v1.0.0** — bootstrapping kit for a new instance.

This is a materially different and more current onboarding path than anything cited from the Space's Grand Synthesis, which relied on six older, non-canonical source documents. Any future consolidation work should start here, not from the Space's philosophy corpus.

## Current Reality Check (Canonical Build Spine v0.2, dated 2026-07-02)

The most current single distillation artifact in the repository is `docs/governance/FLOSSI0ULLK_CANONICAL_BUILD_SPINE_v0.2.md`, dated 2026-07-02 — more recent than every document in the user's Space. It explicitly supersedes two prior "merged upgradeable artifact" documents and states its own executive decision in the project's ternary format: "+1 proceed with the smallest auditable stewarded agent system; 0 hold on deeper sovereignty/autonomy layers until current gates are green". Its concrete, evidence-scoped conclusions are:[^6]

- GitHub (`G-0-B/FLOSS`) is the current canonical development surface; Radicle remains a future sovereignty target, not current fact.[^6]
- Holochain substrate viability is "partially verified, not globally complete" — WASM/hApp/native tests pass, but Tryorama end-to-end integration is not currently green against the 0.6 substrate line. This directly corrects the README's more optimistic "Phase 0 complete" framing found elsewhere in the repo, illustrating why precedence order matters: the Canonical Build Spine (tier 4) is more current and more qualified than the top-level README.[^6]
- SDD and provenance are the source of truth; specs, tests, source registers, and contradiction logs precede any new architecture work.
- KERI, AD4M, hREA, ZK attestations, and autonomous (no-human-gatekeeper) operation are explicitly deferred until a concrete present-tense pain passes the evidence gate.[^6]
- The long-range FLOSSI0ULLK vision is preserved but must not be used as a release criterion; only executable tests, reproducible logs, and traceable evidence gate releases.[^6]

This single document is the most defensible "true current best" available, because it is dated after every other canonical document, explicitly names what it supersedes, and is scoped as "Proposed / Specified" pending maintainer review rather than asserting unverified certainty.

## Prior Consolidation Precedent (Directly Applicable)

`docs/ADRs/ADR-3-Documentation-Consolidation.md`, dated 2025-12-11, already executed exactly the kind of distillation being requested now, at smaller scale. It documented and resolved concrete duplication problems: two conflicting "ADR-1" documents with unrelated content, a mislabeled duplicate README, an executive summary file containing unresolved git merge conflict markers, and four different specification files with unclear, non-semantic version suffixes (`_v_0`, `_v_00`, `_v_000`, `_v_01`). This precedent establishes both a proven method (multi-lens analysis, explicit problem statement, decision record) and a warning: the versioning-suffix confusion it fixed in 2025-12 appears to be recurring, since `docs/architecture/` still contains near-duplicate titles as of the current tree listing (e.g. multiple "Rose Forest ... Holochain" scaffold documents, multiple "Automated-Agent-Orchestration-Report" versions).[^9]

## What a True Distillation Requires Going Forward

Based on the precedence chain, the loading order, and the prior consolidation ADR, a rigorous next-stage distillation should:

- Treat only tiers 1-8 of the Spine's precedence chain as citable capability claims; demote everything else — including the entire Space corpus and most of `docs/research/` and `docs/architecture/` — to "input for triage," matching the Spine's own rule.[^2]
- Resume, rather than restart, the existing `docs/research/2026-05-10-doc-cull-triage-v1.md` triage, since it already has a Keep/Update/Archive/Dispose framework and user-corrected findings in progress (e.g., clarifying that `FLOSSI_U_Founding_Kit_v1.6` is a distinct sibling project and should be relocated rather than culled, and that YumeiCHAN is an active sub-project, not dead exploration).[^4]
- Reconcile the Canonical Build Spine v0.2's more current, qualified claims (Tryorama not fully green) against the top-level README's more optimistic "Phase 0 complete" framing, since these two documents currently disagree and the Spine's precedence order says the governance-tier document should win.[^1][^6]
- Apply the same consolidation method used in ADR-3 (explicit problem statement, multi-lens snapshot, decision record) to the newly-identified duplicate-title cluster in `docs/architecture/` and the parallel Space-file corpus, rather than generating a seventh independent synthesis.
- Preserve, rather than delete, superseded material — the repository's own convention directs archiving to `FLOSS/archive/` with supersession links, never deletion, so that provenance and fork visibility are maintained per the Light principle.[^3][^2]
